## Q1b — **no, your reading is wrong, and the native-rate mix does matter**

`common/pose_to_unisign.py: fps_ratio_for_clip` returns:

```python
return min(1.0, target_fps / src)
```

The `min(1.0, ...)` is the problem. A clip whose native rate is **at or below the target is not
thinned at all** — ratio 1.0, every frame kept. At `--fps 24` that covers every 23.976 and 24.0 fps
clip. On the fetched test set:

| | clips | share |
|---|---:|---:|
| native ≤ 24 fps — **not thinned** at `--fps 24` | **206** | **22.1 %** |
| native > 24 fps — thinned | 725 | 77.9 % |

(Full mix: 29.97→570, 30.0→142, 23.976→116, 24.0→90, 59.94→7, 26.565→4, 25.0→1, 29.94→1.)

So "per-clip thinning makes the native rate irrelevant" is true of the *resulting rate* and false of
the *amount of subsampling applied*. About a fifth of clips receive no subsampling at all, and if dev's
≤24 fps share differs from 22.1 %, the adaptation set contains a different mix of thinned and
unthinned clips than the set it is evaluated on. That is a second distribution difference layered on
the one J9 exists to fix.

**Ask: tally dev's share of clips at ≤24 fps native and report it next to 22.1 %.** If it lands within
a few points, record and move on. If it is materially different, that belongs in the J9 writeup,
because it is a confound on the axis being measured.

## Q1a — accept and record, and here is the bar

Your instinct is right. Two things that make it easier to judge:

**The eval set is already mixed**, so matching dev to a clean 720p is not the bar — matching it to a
*mixture* is. Fetched test clips by source height: **720 → 710**, 470/480 → 45, 360 → 8, and a tail of
others. Roughly 76 % at 720p, ~24 % below it, because those videos were never available higher.

**Resolution skew on dev affects only the training distribution.** Evaluation is pinned to the n=400
test pose set, which does not move. So the failure mode is a model tuned on systematically lower-detail
keypoints than it is then scored on — real, but second-order next to the pose-source shift itself.

**Accept and record** unless 720p yield falls below roughly 60 %, at which point it is worth a second
pass with a different player client rather than carrying it as a caveat. Re-fetching sub-720p clips
that were never *available* at 720p achieves nothing, so condition any re-fetch on the format list,
not on the delivered height.

already fixed.

* If ~1,000 clips recovers a decent share of the frame-rate loss, J9 at ~920 is worth the extraction.
* If it recovers nothing, J9 at this scale is predictably null, and we would be spending board time to
  produce a result the agreed §3 framing already tells us licenses nothing.

That turns Q2 from a judgement call into a measurement, and it answers the data-scale question for the
report either way. **Atisri decides whether to spend the Colab time on it; we are not committing her.**
Keep the dev fetch running regardless, as you proposed — it is unattended and it is the input to both

## Q4 — loaded-and-idle, and **load the pose engine first**

Agreed on loaded-and-idle for the reason you give. One refinement that changes the experiment:
**load the pose engine before the LM**, matching pipeline order. The hypothesis is that a different
resident footprint shifts the LM's energy, and allocator and memory-pool state depend on allocation
*order*, not just on total occupancy. Loading the LM first and the engine second tests a configuration
the pipeline never runs.

## Q7 — yes, one, and it is on J9's critical path. Fixed in this commit.

`unisign/eval_openasl.py` had the same silent-zero. A clip with no `.pkl` under `--poses` is appended
to `missing` and skipped; the run then scores whatever subset happened to exist and writes a result
JSON that looks entirely real. A mistyped `--poses` on the board would have produced
`eval_n400_adapt_ours_fps24.json` scored on a handful of clips, with the shortfall visible only as a
`"missing"` count inside the file.

**A missing-fraction threshold is the wrong fix here, and we tried it first.** The pose directory *is*
the clip selection in this project: `eval_n400_pruned_ours_fps24.json` requests all 976 test names and
legitimately records **576 missing**, 59 %. Any fraction threshold loose enough to permit that is too
loose to catch anything.

So the check is **`--expect-n`**: pass the n you are pairing against and a changed or mistyped
directory fails before scoring. Plus an unconditional abort when nothing at all was scored. Verified:
wrong path aborts with no output file, `--expect-n` mismatch aborts, and a subset scored without
`--expect-n` still succeeds, so the existing n=400 protocol is unchanged.

**For J9 step 3, please run with `--expect-n 400` on both arms.** It is the cheapest guarantee that
the adapted and baseline evals are the same 400 clips, and it fails at the eval rather than at the
bootstrap.
